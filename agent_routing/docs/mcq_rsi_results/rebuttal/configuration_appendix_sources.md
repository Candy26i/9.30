## C. RSI rounds, FA-GRPO and the Success comparator

### Open points

- Ownership: the RSI results belong to the co-authors. The author of this rebuttal owns the Verifier comparison and the manager attribution, so the co-authors should confirm every value and statement in section C before it is posted.
- 'Table 12' is not identified in the repository (no transcription of the submission's numbering). Section C assumes the reviewer's 'Success' comparator is the Success row of the round-3 SFT + GRPO results (the v3+GRPO runs). The co-authors should confirm this. They should also confirm that no Success number in the submission came from the v1 runs: the v1 MedQA three-arm run and the v1 ablation runs also have a Success arm, and the ablation runs' config is not recorded in the repository.
- The paper's own tables conflict with the code, and section C states the code behaviour:
- The setup table describes Success as 'any trajectory ending in a correct answer is a demonstration'. The code draws one successful option per kept record.
- It says each of the 3 rounds has collect, SFT and FA-GRPO. Round 1 has neither collection nor SFT.
- Its single 'Max depth 2' does not hold for the round-1 labels (GPQA depth 1, AQuA depth 3).
- Its acceptance row omits the evaluation-gate condition.
- The GRPO-log caption lists only the accuracy, informativeness and valid-answer conditions, not the calls and call-gap conditions (these never fired).
- Panel B of the label table says 'uses the SFT + GRPO run', but its collectors are v1 checkpoints, not the v3+GRPO run of the main table.
The paper text should be aligned.
- Several v3+GRPO run records are not in the repository: the signed config (rsi_run.json), the git commit, and the FA-GRPO summary.json and step files. For that reason the hyperparameters are given as 'config' or 'code', not 'run'. The learning rate appears only rounded (0.000) in the reports. Which guard criterion stopped each of the 11 rolled-back stages is not recorded. The unpinned HF run backups were not read, and whether backups of the MedQA, GPQA and AQuA v3+GRPO runs exist is not established. Retrieving these files would turn 'config' into 'run'.
- The three MMLU-Pro one-arm runs each ran round-1 FA-GRPO from the same configuration file, the same S_1 adapter (72f44718b09c) and the same pool, yet they recorded different outcomes:
- 24/16, 24/16 and 16/8 steps run / selected;

The records do not state the cause, for example non-determinism or the hardware. Decide whether to disclose this.

They covered the round-1 parity check and the validity gate of every S_k development stage and locked test. MedQA and AQuA failed parity and passed only through this acknowledgement. The acceptance rule is asymmetric: an S_k's validity failure can be acknowledged, but a candidate's cannot. This decided one MedQA rejection (round 3 Static, both at 0.995). Decide how to word this for reviewers.
