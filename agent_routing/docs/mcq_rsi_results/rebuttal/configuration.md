# MARGENT: configuration behind every reported result

This file answers the reviewers' requests for a configuration table, complete training settings, exact split identifiers, executable prompts and checkpoint-selection rules. It states only what the sources record; whatever could not be established is marked "not recorded" and is collected in section 6.

Conventions:

- A source in parentheses closes every table row and every statement. Repository sources are `path:line`, relative to `agent_routing/` at commit `ca5e4fd`; `path@24e6902:line` cites the paper-era commit (`git rev-parse HEAD` in the worktree; src/manager/mcq_rsi/sft.py:11-13).
- "paper assets, FILE" is a file of the HF dataset `MaliDDD/agent-routing-9b-assets` @ `e240a6a8b934637418d925aa78efba431fc1fc74` (below: **A**), stored in `snapshots/assets_0814.tgz` (sha256 `13ee552afb72`), `snapshots/aqua_arc_rescue_0817.tgz` (`c45eee483f0f`) or `small_assets.tgz` (`c08c82863b99`); these files are not in the repository (src/manager/mcq_rsi/benchmarks.py:20-21,136-138).
- The split manifests `data/mcq_rsi/<bench>_splits.json` are single-line JSON files, so they are cited as `:1` plus the key; members of archives are cited as "TARBALL (member PATH)" (src/manager/mcq_rsi/splits.py:434).
- Three kinds of result are kept apart: **single-pass S_1** (the paper's one-round SFT manager and the numbers the paper reports for it), **RSI S_1** (the registered S_1 checkpoint re-evaluated by the RSI harness on the development pools and the locked tests) and **replay** (the matched-budget replay analysis on the development pools) (docs/mcq_rsi_results/paper_assets/build_data.py:268-283; src/manager/mcq_rsi/controller.py:803-804).

The paper's Table 4 prints 64.5 / 0.340, where 0.340 is the call rate of the evaluation log and the average number of calls is 0.36 (src/manager/mcq_rsi/benchmarks.py:244,355-356).
- GPQA: the 148 labels come from the depth-1 collection on 200 roots (`counterfactual_records.jsonl`, sha256 `c5d9c8a7ec7c`). A depth-2 tree on the same roots exists separately (`MaliDDD/marginal-gpqa_marginal_9b_d2` @ `04a2152827d196c21e1350e4042fe2bd83699b29`, sha256 `3027ed1418bc`) and is what the RSI code uses as round-1 records; neither seed 0 nor the depth-2 tree reproduces the 148-row file (src/manager/mcq_rsi/benchmarks.py:281-290,295-300; src/manager/mcq_rsi/importer.py:234-236).
- AQuA-RAT: the collection ran at depth 3 (documented command: `--mv_n_samples 400 --mv_max_depth 3 --mv_temperature 0 --mv_max_commit_rescue_ratio -1`). By arithmetic on the row counts (not read from the file) the 402 rows are 132 commit rows plus 126 one-call and 6 two-call rescues, with no three-call trajectory. The same directory also holds `manager_sft_marginal_d2_ratio1.0.jsonl` (402 rows, sha256 `2c1af5294d62`) with the same decision counts and a different 52 commit rows; which of the two files `sft_1.0` was trained on is not established (AQUA_ARC_BENCHMARKS.md:78,163-164; src/manager/mcq_rsi/benchmarks.py:339-342,358-361; docs/mcq_rsi_results/paper_assets/margent_paper_tables.json:8).
- Root sampling: the roots are the first n questions of `random.Random(42).shuffle(paper train pool)`, and all four manifests record `meta.paper_sampler_reproduced = true` (src/manager/marginal_value.py:483-486; src/manager/mcq_rsi/splits.py:78-82,259; `data/mcq_rsi/<bench>_splits.json:1`, key meta).
- Collection procedure: stage `build_marginal_sft`; greedy decoding (temperature 0.0, at most 512 new tokens), thinking disabled, three tool schemas, a probe user message for the direct answer and after each forced call. Each not-yet-used advisor is forced breadth-first, the Verifier receives the current draft, expansion stops at the first depth that contains a success, and a question answered correctly without a call is expanded to depth 1 only (src/manager/marginal_value.py:41-51,152-175,200-210,264-296,534-626; src/pipeline/stages.py:834-852).
- Label rule: the target is "commit" when the direct answer is correct, otherwise the shortest advisor sequence whose revised answer is correct, with ties broken by `random.Random(seed + example_id).choice` (seed 42); a question with no successful branch yields no row. Ground truth only selects the trajectory and is never substituted for a model answer (src/manager/marginal_value.py:8-14,299-318,628-630).
- Commit cap: commit records are shuffled with `random.Random(seed)` and cut to int(rho x number of rescue records); every rescue record is kept. The three supplied collection reports record `max_commit_rescue_ratio` = -1.0, so the cap was applied afterwards, when the files `manager_sft_marginal_ratio<rho>.jsonl` were written; the registry states that `_balance_records` reproduces those files row for row (src/manager/marginal_value.py:446-459; paper assets, `outputs/manager/<run>/marginal_value/marginal_value_report.json`; tests/test_mcq_rsi_registry.py:121).
- One SFT row: a commit row has the response `DRAFT_ANSWER_X\nANSWER_X`; a rescue with k calls yields k call rows (`DRAFT_ANSWER_<draft>` plus one tool call) and one commit-after-call row. Every token of the response is supervised, including the manager's own draft letter on call rows (src/manager/marginal_value.py:85-96,381-443; src/manager/mcq_rsi/sft.py:41-47).
- Consistency with the paper's Table 1: the MMLU-Pro and AQuA rows agree with the collection reports. The MedQA row (91.75 % after one call, 92.25 % best measured) does not agree with the `medqa_marginal_9b_d2_400` report (oracle accuracy 0.915), and the GPQA row comes from a tree of depth 2 or more, whereas the S_1 labels come from the depth-1 collection (docs/mcq_rsi_results/paper_assets/margent_paper_tables.json:2-8; paper assets, `outputs/manager/<run>/marginal_value/marginal_value_report.json`; src/manager/mcq_rsi/benchmarks.py:298).
- Sibling checkpoints: "all commit" managers (same collection and SFT recipe, every target a commit) are `managers/<run>/sft_allcommit` in **A** for MedQA, MMLU-Pro and AQuA and the HF model `MaliDDD/gpqa_marginal_9b-sft_allcommit` (fetched without a pinned revision); the rebuttal re-trainings `<bench>_seed1` and `<bench>_seed2` use `--seed K`, 10 epochs, learning rate 1e-5, maximum length 4096, batch 1 x accumulation 8, but their rendered inputs differ from the paper-era ones (`"tool_calls": null` in every tool schema) and no result or digest is recorded yet (scripts/pod_ops/verifier_grid_chain.sh:97,101-105; scripts/pod_ops/seed_sft_chain.sh:2-9,16,23-39; src/manager/mcq_rsi/sft.py:15-22; tests/test_mcq_rsi_sft.py:114-116).

## 2. Advisors

- What was served: in every paper number and every RSI number the Extractor, Reasoner and Verifier were the base model `Qwen/Qwen3.5-9B` answering under each role's system prompt. The role-specific LoRA adapters exist and are registered, but the paper-era server did not apply them. The decision record of 2026-10-02 (D14) reads: "The paper-era server never applied the advisor LoRAs: vLLM dropped their unmatched keys (§5), and the original HF adapters served that way are byte-identical to the base. So every paper number, the locked S_1 managers and their round-1 labels come from the base model answering under each role's prompt." (docs/MCQ_RSI_RUNBOOK.md:60; src/manager/mcq_rsi/advisors.py:84-88).
- Mechanism: the adapters were trained on `Qwen3_5ForCausalLM`, so their keys are `base_model.model.model.layers.N...`; vLLM 0.26.0 serves the checkpoint as `Qwen3_5ForConditionalGeneration`, whose language-model modules are `language_model.model.layers.N...`, and its LoRA name mapping matches no module. The adapter "loads" and the request is answered by the plain base model, with nothing above debug level reporting it (src/manager/mcq_rsi/serving.py:3-13; scripts/start_mcq_advisors.sh:23-28; docs/MCQ_RSI_RUNBOOK.md:180-185).
- Evidence: the raw files are archived on HF (`MaliDDD/margent-mcq-rsi`, `logs/d14_evidence/summary.json`). The summary tracked in the repository covers 20 prompts each for the Extractor and the Verifier: for the Verifier the original adapter as served returned text identical to the base model on 20 of 20 prompts (median similarity 1.0), and a copy with renamed keys on 0 of 20 (0.345); for the Extractor the original adapter was identical on 5 of 20 prompts (median similarity 0.924) and the renamed copy on 0 of 20 (0.392); no Reasoner entry is recorded. The 20-of-20 identity is therefore recorded in the repository for the Verifier only (docs/mcq_rsi_results/paper_assets/appendix.json:383-398; docs/mcq_rsi_results/paper_assets/build_appendix_data.py:6-7,47-49).
- Configuration: all 13 files `configs/mcq_rsi_*.json` set `"advisor_mode": "base"`; the controller default and the manual CLI default are "lora", so the setting comes from the config. In base mode the server is started without LoRA flags and every request names the base model (configs/mcq_rsi_medqa.json:8; src/manager/mcq_rsi/controller.py:109-111; src/manager/mcq_rsi/__main__.py:392-393; scripts/start_mcq_advisors.sh:137-141).
- Do the adapters help when loaded correctly: on 754 pooled development questions, accuracy with the base model / the paper LoRA / a retrained LoRA is 79.7 / 80.4 / 80.8 for the Extractor, 80.6 / 80.1 / 79.6 for the Reasoner and 81.4 / 79.8 / 78.2 for the Verifier; the runbook concludes that neither set of adapters beats the base model (docs/mcq_rsi_results/paper_assets/tab/tab_app_advisors.md:15-19; docs/MCQ_RSI_RUNBOOK.md:60).

## 4. RSI rounds and FA-GRPO

- Round structure: round 1 trains nothing; the imported S_1 is evaluated on `dev` and, for arms with GRPO, FA-GRPO is run from S_1 on `grpo_r1`, giving one G_1 shared by those arms. From round 2 each arm runs collect, select, SFT initialised from G_(k-1), a development evaluation, and (arms with GRPO) FA-GRPO and its development decision (src/manager/mcq_rsi/controller.py:16-38,293,308-357).
- Collection in rounds 2 and later: maximum depth 2, seed 42 (tie-break), batch size 1, root mode "policy" (the root is the manager's own greedy deployment turn, restricted to the legal actions), 400 new train questions per round that are never advisor-SFT questions (GPQA: the same 200 roots). The cap rho and its seed are the registry values of section 1 (configs/mcq_rsi_medqa.json:30-39; src/manager/mcq_rsi/collect.py:8-24; src/manager/mcq_rsi/select.py:164-165; src/manager/mcq_rsi/splits.py:14-16,49).
- Manager SFT in rounds 2 and later: 3 epochs, learning rate 1e-5 with linear decay to 0 and no warmup, batch 1 x accumulation 8, maximum length 4096 (GPQA 16384), seed 42, bf16, paper-era rendering of the tool schemas; the LoRA of G_(k-1) is continued with a new AdamW optimizer and only the rows of round k are trained. `draft_supervision` is "all" in v1 (every token trained, as in the paper), "commit_rows" in v2 and "none" in v3 (no draft token is trained) (configs/mcq_rsi_medqa.json:40-48; configs/mcq_rsi_gpqa.json:45; src/manager/mcq_rsi/sft.py:3-5,41-48,54-65,357,373-379; configs/mcq_rsi_medqa_v2.json:47; configs/mcq_rsi_medqa_v3.json:47).

- Acceptance rule (per round, on the development pool): G_k is accepted only if (a) neither the G_k nor the S_k evaluation fails the evaluation gate, (b) accuracy is at least S_k - 0.01, (c) calls per question are at most S_k + 0.15, (d) the call gap is at least s - 0.5 x abs(s), where s is the call gap of S_k, and (e) the FA-GRPO stage was informative. Otherwise G_k := S_k and S_k goes to the next round. The call gap is P(at least one call, given a wrong initial draft) - P(at least one call, given a correct initial draft) (src/manager/mcq_rsi/evaluate.py:293,308,361-389; src/manager/mcq_rsi/controller.py:998-1015; configs/mcq_rsi_medqa.json:70-73).
- Evaluation gate (every evaluation): no malformed tool call, valid-answer rate 1.0, no advisor failure, no error payload in a tool output; an S_k development evaluation or a locked-test evaluation whose only failure is unparsed answers passes after a recorded acknowledgement if the valid-answer rate is at least 0.99 (src/manager/mcq_rsi/advisors.py:113-126; src/manager/mcq_rsi/evaluate.py:340-354; src/manager/mcq_rsi/controller.py:932-949,958-961).
- S_k is never selected on the development pool: it is only flagged when calls per question exceed 1.5 or accuracy drops by more than 0.03 against the previous round, and a flag does not change the path. The round-1 parity gate requires S_1 within 0.02 accuracy and 0.05 calls of the registry targets; it failed and was acknowledged for MedQA (0.79 / 0.37 against 0.82 / 0.405) and AQuA (0.732 / 0.791 against 0.78 / 0.894), passed for MMLU-Pro and does not apply to GPQA (src/manager/mcq_rsi/evaluate.py:392-401; configs/mcq_rsi_medqa.json:74-81; src/manager/mcq_rsi/controller.py:835-867; docs/mcq_rsi_results/results/grpo_grid_locked_tests_v3g.tar.gz (members `runs/{medqa,aqua}_v3g/r1/S1_dev/decision.json`); docs/mcq_rsi_results/results/grpo_grid_mmlu_pro_v3g_split.tar.gz (member `runs/mmlu_pro_v3g_dyn/report.md`, section "Gates")).
- Final-checkpoint rule (per condition): the tested checkpoints are S_1 and, for each arm, the last round's resolved checkpoint (G_R, or S_R if GRPO was rejected or the arm has no GRPO). The checkpoint with the best development result is never used, and inside a GRPO stage the checkpoint is the last guard-passing step. The locked test runs once per such final (src/manager/mcq_rsi/controller.py:1568-1594,1620-1643; docs/MCQ_RSI_RUNBOOK.md:58).
