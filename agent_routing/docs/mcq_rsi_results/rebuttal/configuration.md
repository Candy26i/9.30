# MARGENT: configuration behind every reported result

This file answers the reviewers' requests for a configuration table, complete training settings, exact split identifiers, executable prompts and checkpoint-selection rules. It states only what the sources record; whatever could not be established is marked "not recorded", whatever a pinned source holds but was not opened is marked "not read", and both are collected in section 6.

Conventions:

- A source in parentheses closes every table row and every statement. Repository sources are `path:line`, relative to `agent_routing/`, at commit `0693275` (HEAD of feat/mcq-rsi-controller on 2026-11-26). Between `9299512` and `0693275` no cited file changed except the allc result tables under `docs/mcq_rsi_results/rebuttal/` and the new `scripts/mcq_verifier_grid_seeds.py`; files marked "untracked" are in the working tree only. `path@24e6902:line` cites the paper-era commit (`git rev-parse HEAD`; `git diff --stat 9299512 0693275`; src/manager/mcq_rsi/sft.py:11-13).

Notes on the table:

- MedQA: the registered S_1 is not the paper's locked checkpoint. The registry states "S_1 substitutes d2_400/sft_3.0 (seed 0) for the locked sft_3.0_s1, which is not on HF", and the results page describes it as trained with the same configuration. The registry holds the targets 0.82 / 0.405 for this substitute on the MedQA development pool, and a recorded paper-era evaluation of it on that pool exists (`medqa_9b_d2400_ev_r3`); that the aggregate of this evaluation is 0.82 / 0.405 is not stated in the repository (section 5). The paper's Table 4 reports the three-seed mean 80.5 / 0.517 (src/manager/mcq_rsi/benchmarks.py:200,202; docs/mcq_rsi_results/margent_rsi_results.html:232,248; tests/fixtures/mcq_rsi/paper_medqa_replay.json:1, key source.eval; docs/mcq_rsi_results/paper_assets/margent_paper_tables.json:18-19).
- MedQA training seeds: the repository records three development results, SEEDS = [(80.5, 52.5), (81.5, 55.5), (79.5, 47.0)] (accuracy in %, questions with a call in %), with mean 80.5 +- 1.0 and 51.7 +- 4.3 (sample SD). The pair 82.0 % / 0.405 calls per question is the registry target of the registered S_1 and is not an entry of SEEDS; which checkpoint produced which entry is not recorded (docs/mcq_rsi_results/paper_assets/scripts/tab_final.py:122,155; docs/mcq_rsi_results/paper_assets/tab/tab_final_reliab.md:5-6; src/manager/mcq_rsi/benchmarks.py:200).
- MMLU-Pro: S_1 is the depth-2 `sft_2.0` of the assets, not the depth-1 HF model repository `mmlu_marginal_9b-sft_2.0`. The paper's Table 4 prints 64.5 / 0.340, where 0.340 is the call rate of the evaluation log and the average number of calls is 0.36 (src/manager/mcq_rsi/benchmarks.py:244,355-356).
- GPQA: the 148 labels come from the depth-1 collection on 200 roots (`counterfactual_records.jsonl`, sha256 `c5d9c8a7ec7c`). A depth-2 tree on the same roots exists separately (`MaliDDD/marginal-gpqa_marginal_9b_d2` @ `04a2152827d196c21e1350e4042fe2bd83699b29`, sha256 `3027ed1418bc`) and is what the RSI code uses as round-1 records; neither seed 0 nor the depth-2 tree reproduces the 148-row file. The report of the depth-1 collection was not read. The GPQA counts in the table are derived from the row counts that two training logs print (148 for S_1, 160 for the all-commit sibling), on the assumption that the all-commit log trains the uncapped file of the same depth-1 collection, as its name and the other three benchmarks indicate. The derived 86 commit records of 200 are 43.00 %, which is the commit column of the paper's Table 1 (src/manager/mcq_rsi/benchmarks.py:281-290,295-300; src/manager/mcq_rsi/importer.py:234-236; paper assets, logs/sft_gpqa9b_2.0.log, logs/sft_gpqa9b_allcommit.log; src/manager/marginal_value.py:446-459; docs/mcq_rsi_results/paper_assets/margent_paper_tables.json:7).
- AQuA-RAT: the collection ran at depth 3 (report field max_depth 3; documented command: `--mv_n_samples 400 --mv_max_depth 3 --mv_temperature 0 --mv_max_commit_rescue_ratio -1`). The report's `preferred_depth_counts` are 217 / 126 / 6 for 0 / 1 / 2 calls and hold no three-call entry, so the 402 rows are 132 commit rows (the cap int(1.0 x 132) applied to the 217 commit records), 252 rows of the 126 one-call rescues and 18 rows of the 6 two-call rescues. The one-call count agrees with Table 1: (85.75 - 54.25) % x 400 = 126. The same directory also holds `manager_sft_marginal_d2_ratio1.0.jsonl` (402 rows, sha256 `2c1af5294d62`) with the same decision counts and a different 52 commit rows; which of the two files `sft_1.0` was trained on is not established (paper assets, `outputs/manager/aqua_marginal_9b_v1/marginal_value/marginal_value_report.json`; AQUA_ARC_BENCHMARKS.md:78,163-164; src/manager/mcq_rsi/benchmarks.py:339-342,358-361; docs/mcq_rsi_results/paper_assets/margent_paper_tables.json:8).
- Root sampling: the roots are the first n questions of `random.Random(42).shuffle(paper train pool)`, and all four manifests record `meta.paper_sampler_reproduced = true` (src/manager/marginal_value.py:483-486; src/manager/mcq_rsi/splits.py:78-82,259; `data/mcq_rsi/<bench>_splits.json:1`, key meta).
- Collection procedure: stage `build_marginal_sft`; thinking disabled, three tool schemas, a probe user message for the direct answer and after each forced call. Each not-yet-used advisor is forced breadth-first, the Verifier receives the current draft, expansion stops at the first depth that contains a success, and a question answered correctly without a call is expanded to depth 1 only. The probe temperature 0.0 and the limit of 512 new tokens are the defaults of `--mv_temperature` and `--mv_max_new_tokens`: the collection reports do not record either value, and only the documented AQuA command sets the temperature explicitly (`--mv_temperature 0`). The collection seed 42 is confirmed by the reproduction of the root sample and of the tie-breaks (src/manager/marginal_value.py:41-51,66-67,152-175,200-210,264-296,367-378,534-626,649-658; src/pipeline/stages.py:834-852; src/pipeline/cli.py:289-292; AQUA_ARC_BENCHMARKS.md:163; tests/test_mcq_rsi_select.py:179-183; src/manager/mcq_rsi/splits.py:259).
- Label rule: the target is "commit" when the direct answer is correct, otherwise the shortest advisor sequence whose revised answer is correct, with ties broken by `random.Random(seed + example_id).choice` (seed 42, confirmed by a test that re-derives every stored label); a question with no successful branch yields no row. Ground truth only selects the trajectory and is never substituted for a model answer (src/manager/marginal_value.py:8-14,299-318,628-630; src/manager/mcq_rsi/select.py:42; tests/test_mcq_rsi_select.py:179-183).
- Commit cap: commit records are shuffled with `random.Random(seed)` and cut to int(rho x number of rescue records); every rescue record is kept. The three collection reports that were read record `max_commit_rescue_ratio` = -1.0, so the cap was applied afterwards, when the files `manager_sft_marginal_ratio<rho>.jsonl` were written. The MedQA directory holds files of 129 rows (rho 0), 191 (rho 1), 253 (rho 2), 315 (rho 3) and 433 rows (`manager_sft_marginal.jsonl`, no cap), which is 129 rows of the 62 rescues plus int(rho x 62) commit rows. The registry states that `_balance_records` reproduces the S_1 label files, and a test that runs when the round-1 data has been imported checks all four row for row with the tie-break seed 42 and the cap seed 0 (GPQA 42). On the rebuttal pod on 2026-11-26, `python -m src.manager.mcq_rsi select --arm dynamic` on the imported round-1 records (GPQA: its depth-1 `label_records`) reproduced the rows of each S_1 label file in the same order (prompt and response equal; 315 / 331 / 148 / 402 rows; the selector only adds a `split` field) (src/manager/marginal_value.py:446-459; paper assets, `outputs/manager/<run>/marginal_value/marginal_value_report.json`; paper assets, `outputs/manager/medqa_marginal_9b_d2_400/marginal_value/`; tests/test_mcq_rsi_select.py:162-196; src/manager/mcq_rsi/select.py:5-9,42; src/manager/mcq_rsi/benchmarks.py:103,299-300,358; scripts/pod_ops/seed_sft_chain.sh:15-16,35-43; rebuttal pod, 2026-11-26, log `logs/verifier_grid/seed_sft.log`).
- One SFT row: a commit row has the response `DRAFT_ANSWER_X\nANSWER_X`; a rescue with k calls yields k call rows (`DRAFT_ANSWER_<draft>` plus one tool call) and one commit-after-call row. Every token of the response is supervised, including the manager's own draft letter on call rows (src/manager/marginal_value.py:85-96,381-443; src/manager/mcq_rsi/sft.py:41-47).
- Consistency with the paper's Table 1: the MMLU-Pro and AQuA rows equal the values that the counts of their collection reports give. The MedQA row (91.75 % after one call, 92.25 % best measured) does not agree with the `medqa_marginal_9b_d2_400` report, whose counts give 90.25 % and 91.5 % (oracle accuracy 0.915), and the GPQA row comes from a tree of depth 2 or more, whereas the S_1 labels come from the depth-1 collection. The counts derived for that depth-1 collection (table above) support this: 86 of 200 = 43.00 % equals the commit column of Table 1, while (86 + 37) / 200 = 61.5 % differs from its one-call column, 65.00 % (docs/mcq_rsi_results/paper_assets/margent_paper_tables.json:2-8; paper assets, `outputs/manager/<run>/marginal_value/marginal_value_report.json`, field preferred_depth_counts; paper assets, logs/sft_gpqa9b_2.0.log, logs/sft_gpqa9b_allcommit.log; src/manager/mcq_rsi/benchmarks.py:298).
- Sibling checkpoints of S_1: the "allcommit" managers use the same collection and SFT recipe as S_1 and are trained on `manager_sft_marginal.jsonl`, in which every commit row is kept (no commit cap, rho = -1); they are not trained on commit rows only. The MedQA, MMLU-Pro and AQuA adapters are `managers/<run>/sft_allcommit` in **A** at the pinned revision; the GPQA adapter is the HF model `MaliDDD/gpqa_marginal_9b-sft_allcommit`, fetched without a pinned revision. ## 4. RSI rounds and FA-GRPO

- Round structure: round 1 has no collection and no SFT, because S_1 is imported. S_1 is evaluated on `dev`, and for arms with GRPO FA-GRPO is run from S_1 on `grpo_r1` and its candidate goes through the acceptance decision; within one run this gives one G_1 shared by those arms. Round-1 outcomes of the v3+GRPO runs: MedQA rejected; MMLU-Pro, which ran as three one-arm runs after a first joint run had stopped during its locked test (section 3), three separate stages, all rejected; GPQA accepted but rolled back to step 0, which is S_1; AQuA accepted at step 32 of 40, so G_1 differs from S_1 there. From round 2 the `dynamic` and `success` arms collect and select, the static arms reuse the round-1 label file without collection (`static_shadow_collect` is false), and every arm runs SFT initialised from G_(k-1), a development evaluation and, for arms with GRPO, FA-GRPO and its development decision (src/manager/mcq_rsi/controller.py:16-38,293,308-357; src/manager/mcq_rsi/grpo.py:885-888; docs/mcq_rsi_results/paper_assets/tab/tab_grpo_log.md:5,13,16,19,23,31; scripts/pod_ops/mcq_supervisor_v3g2.py:4-6; configs/mcq_rsi_medqa.json:104).
